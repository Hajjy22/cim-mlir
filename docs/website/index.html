A compiler for compute-in-memory hardware

An MLIR dialect, eight passes, and a runtime ABI for hardware that computes inside the memory array — where writing weights costs orders of magnitude more than using them.

The problem

Compute-in-memory hardware exists and some of it ships. What does not exist is a way to take a normal neural network — a PyTorch model, an ONNX file — and run it on that hardware without hand-writing assembly or using a vendor's closed, single-chip compiler.

Every vendor rebuilds this layer privately. Academic work solved it for exactly one chip. The result is that this hardware has no software gravity, and hardware without software gravity does not get adopted. This project is an attempt at the missing layer: one abstraction that several different CIM/PIM parts can be described in, and a compiler that targets the abstraction rather than any single chip.

Five axes of variation

Real CIM/PIM hardware varies along five axes. A useful abstraction has to parameterize all five and assume none of them.

The unifying abstraction: the tile

All of it is modeled as an array of tiles. A tile is a fixed-capacity 2D compute-and-storage unit that can hold a weight sub-matrix and perform a matrix-vector multiply against it.

This is deliberately the lowest common denominator. A UPMEM DPU is a tile. A 256×256 digital SRAM macro is a tile. An analog crossbar is a tile. A near-memory RISC-V cluster is a tile. Everything above this line in the compiler is written against that one shape.

The asymmetry the compiler exploits

On a GPU, loading weights and computing with them cost roughly comparable amounts. On CIM hardware they differ by orders of magnitude, and on non-volatile CIM the asymmetry is extreme: writes to MRAM or RRAM are slow and energy-hungry, but once written the weights sit there at essentially zero standby leakage indefinitely.

So the central optimization problem is not scheduling the math. It is:

Given N physical tiles and a model with M weight sub-matrices where M > N, decide which weights live where and when, so that total reprogramming cost is minimized.

That is a placement and eviction problem, and no mainstream ML compiler solves it, because no mainstream hardware has this cost structure. It is the thesis of the project — the pass that implements it is the one worth having.

The useful part: because a model graph is static, the whole use sequence is known at compile time. That makes Belady's furthest-in-future policy — provably optimal, and impossible for any runtime cache to implement because it requires knowing the future — actually available here.

Memory spaces

Three address spaces are modeled as memory-space attributes on memref. Transfers between them are always explicit cim.copy ops — never implicit.

The pipeline

Eight passes, run in order. They compose as one chain: a real matmul goes in at the top and real runtime calls come out at the bottom.

  1. cim-detect

    Finds linalg.matmul-shaped ops with a constant INT8 weight operand and annotates them as candidates. Detection and conversion are separate passes so each is testable alone — this one only marks, it never rewrites.

  2. cim-partition

    Cuts a logical weight matrix into tile-sized sub-matrices and emits the cim ops that operate on them. A ragged edge is zero-padded up to the next tile multiple and cropped back on write-out, rather than special-cased.

    Refuses a plain linalg.matmul (needs output-major weights) and a matmul with more than one output row. Both leave the original op intact with a warning, so the module stays correct and is simply not offloaded.

  3. cim-placement

    The flagship. Recovers the execution order of weight sub-matrices from the IR, solves it with Belady, and rewrites: redundant programs are erased and their consumers rewired to the weights already resident in the tile. It also hoists a program out of a loop when that tile is provably untouched for a whole iteration, and separately solves the whole flattened multi-iteration sequence so it can report how far its own output sits from the unrestricted optimum — see the note in the status section for that number and why it stops where it does.

    Note weight identity is not SSA identity — two matmuls reading one weight global produce different SSA values for the same physical weights, so identity is the root allocation, byte offset and shape. Keying on the value would find no reuse while appearing to work.

  4. cim-schedule

    Decides where a cim.barrier has to sit. Work accumulates un-synchronized until something actually depends on it; the barrier goes immediately before that dependent op, and a block always flushes before its own terminator.

    Scope v0.1 never reorders or overlaps anything. Double-buffering program against mvm is later work, gated on the target declaring it can.

  5. cim-insert-transfers

    Inserts a cim.copy wherever an op needs an operand in a different space than it currently lives in, then hoists redundant copies out of loops when the source is loop-invariant — inserted once before the loop instead of once per iteration.

  6. cim-legalize-precision

    Inserts a cim.requantize after each partial-sum reduction so an i32 accumulator is narrowed to the target's declared effective bits, retyping the downstream chain where it safely can.

    Scope scale is always 1.0 and zero-point 0, because v0.1 has no calibration step anywhere to derive anything else from. Inventing calibration data the pass could not validate would be the exact "plausible but wrong" failure this project avoids.

  7. cim-lower-to-target

    Turns cim ops into real func.calls against the runtime's C ABI, with every status checked by an assertion rather than ignored. The output goes through MLIR's standard LLVM pipeline, a translator and a linker, and comes out as a binary that runs. Handles straight-line code plus one level of loop nesting, hoisting each buffer it allocates out of the loop so it is reused rather than leaked per iteration.

    Refuses a cim op nested deeper than one loop level, a loop carrying values, and a slice of a device buffer that is not one contiguous byte range.

  8. cim-cost-report

    Walks the final IR and emits a JSON cost report, weighting each op by the product of its enclosing loops' trip counts — a hoisted program runs once no matter where it sits textually, one left inside a loop runs trip-count times. It reuses the same cost model the benchmark tool uses, rather than a second one that could drift.

    Refuses to guess: an op under a loop whose trip count is not a compile-time constant is excluded from the totals and flagged in the JSON header, not assumed to fire once.

Dialect reference

Nine ops, three types (!cim.device, !cim.tile, !cim.resident) and one memory-space attribute. Grouped by what they are for.

Device and tiles

cim.device_open

Opens a target by name. Everything else needs one of these.

%dev = cim.device_open {target = "erbium-8t"} : !cim.device<"erbium-8t">

cim.tile_alloc

Claims one physical tile. The id is what cim-placement writes its answer into.

%t = cim.tile_alloc %dev {id = 0 : i64}
     : (!cim.device<"erbium-8t">) -> !cim.tile<256x256xi8>

cim.tile_free

Releases a tile.

cim.tile_free %t : !cim.tile<256x256xi8>

Compute

cim.program

Writes weights into a tile. This is the expensive op — the entire placement pass exists to emit fewer of these. Its result is a !cim.resident, the proof that particular weights are in that particular tile right now.

%r = cim.program %tile, %weights {cost_ns = 12000 : i64, cost_pj = 480000 : i64}
     : (!cim.tile<256x256xi8>, memref<256x256xi8, #cim.space<host>>)
       -> !cim.resident<256x256xi8>

cim.mvm

Matrix-vector multiply against resident weights. Activations must live in near space. The accumulator is wider than the inputs — i8 in, i32 out.

%out = cim.mvm %r, %act {accumulate = false}
       : (!cim.resident<256x256xi8>, memref<256xi8, #cim.space<near>>)
         -> memref<256xi32, #cim.space<near>>

cim.reduce_partial

Sums the partial results from a weight matrix that spanned more than one tile in the K dimension. Variadic — an N-operand reduce becomes N−1 runtime calls.

%sum = cim.reduce_partial %p0, %p1
       : (memref<256xi32, #cim.space<near>>, memref<256xi32, #cim.space<near>>)
         -> memref<256xi32, #cim.space<near>>

cim.requantize

Narrows a wide accumulator back to the target's effective bits, with rounding half away from zero and a signed clamp. The arithmetic is done by the runtime, not re-emitted as IR, so there is only ever one implementation of the formula.

%q = cim.requantize %sum {scale = 0.00392 : f32, zero_point = 0 : i32,
                          effective_bits = 8 : i32}
     : memref<256xi32, #cim.space<near>> -> memref<256xi8, #cim.space<near>>

Movement and ordering

cim.copy

Moves a buffer between address spaces. Always explicit — this is what keeps the cost model honest.

%d = cim.copy %src : memref<256xi8, #cim.space<host>>
                  to memref<256xi8, #cim.space<near>>

cim.barrier

Synchronizes all outstanding work on a device.

cim.barrier %dev : !cim.device<"erbium-8t">

The runtime boundary

Below the dialect sits cimrt, a plain C ABI — open a device, allocate and free buffers, write and read them, program a tile, run an mvm, reduce, requantize, synchronize. The compiler emits calls against this header and nothing below it.

Two implementations sit behind that header. A functional simulator does real INT8 arithmetic and keeps real profiling counters, so a compiled program produces genuine numbers and genuine op counts. An Erbium hardware backend exists as a stub that reports "no device" from every entry point — honestly unimplemented rather than quietly faked.

The last pass's output is a real artifact, not a shape. It goes through MLIR's standard conversion pipeline, a translator to LLVM IR, a C compiler and a linker, against the real runtime library — and the resulting binary is executed as part of the test suite, checked against values that only come out right if the hardware path actually worked.

cim-opt → mlir-opt --convert-to-llvm → mlir-translate → clang → link libcimrt.a
                                                                    ↓
                                                             a binary that runs

Placement across iterations — the number, and why it stops there

The benchmark table quotes the standalone simulator: 8538 weight-programming ops against 16000 for LRU and FIFO under 2× spill pressure. The compiler does not emit exactly that, and the distance is now measured rather than described.

On the same shape — 16 weight blocks over 8 tiles — the compiler emits 7 + 9×T programs, so 9007 at 1000 inferences against the optimum's 8538. That is a 5.5% gap, and against LRU's 16000 it is a 43.7% reduction where the table claims 47%. Both numbers and the gap between them are now fields in the compiler's own cost report, so this stays checked rather than asserted.

The residual is not a missing optimization. 7 + 9×T is tiles−1 weights held permanently plus blocks−(tiles−1) reprogrammed each iteration, which is the best any single loop body can do: a weight that nothing in the body programs is never written and so holds a tile forever, and at most tiles−1 weights can do that. The unrestricted schedule wins the remaining 5.5% only by varying how many weights it programs from one iteration to the next — 8 on some, 9 on others. A loop body executes a fixed set of ops every time round, so it cannot emit a varying number of them.

That last point is worth stating because the obvious fix does not work. It looks like the optimal schedule merely rotates which tile holds which weight, which a tile index computed from the loop counter could express. It does not: the count varies, not just the assignment, and no choice of indices changes a fixed body's op count. There is a test pinning that, specifically so the next person does not spend the dialect change to buy nothing.

Now reached deliberately, not by accident

Until recently the compiler reached that per-iteration bound by accident rather than by aiming at it: an eviction scan that starts at tile 0 and stops at the first weight with no future use happens to leave tile 0 absorbing the whole spill and every other tile written exactly once — precisely the condition that marks a weight as permanently resident. A reasonable-looking cleanup of that scan would have spread evictions instead, silently degrading the workload to what a plain LRU cache does. A structural test guards exactly that regression, because the numerical suites cannot see it — a compiler that holds nothing permanently still computes identical values, just more of them per iteration.

The bound is now aimed at directly. A pin-and-stream schedule pins the tiles−1 most-used weights to permanent tiles by occurrence count (ties broken by first-use order) and streams everything else through the one remaining tile via a single-tile Belady sub-solve — single-tile solves are trivial and deterministic, since there is never a victim to choose between. The compiler computes both this schedule and the ordinary per-block solve for every constant-trip loop and takes whichever is strictly cheaper, so every case where the two already agreed is rewritten byte-for-byte unchanged.

When every weight in a loop body is used exactly once — cim-partition's own shape, and every workload in the benchmark table above — pin-and-stream is provably optimal, checked by exhaustive search over every permutation up to 7 distinct weights against every tile count. When a weight repeats within one body the pin choice becomes a heuristic (the true optimum there is a residency fixed-point problem this project does not solve exactly), but it is proven never worse than pinning nothing at all, and its own output always replays as a genuine fixed point — checked exhaustively on small alphabets and on 500 random instances. That repeated-weight case is exactly the one the old accidental mechanism could fail on; there is now a test built specifically to hit it, on both the structural IR shape and the computed numbers.

On the cost numbers

The target file's cost figures are estimates, not measurements, and the file says so in a provenance field the tools read and print a warning about on every run. Energy figures derived from them inherit that uncertainty. The counts are of weight programming, not end-to-end wall clock.
